## 1. Shape: two modular backends, one database

```
tuw-website  ──  storefront API (Next.js route handlers)  ─┐
                                                           ├──  Neon Postgres (db/)
tuw-admin    ──  admin API (Next.js route handlers)       ─┘
```

Not microservices. Each app is a **modular monolith**: one deployable,
split inside into independent modules. A change to returns touches the
returns module — not five services, and not the other modules.

## 2. Module layout (inside each app)

```
src/server/
  modules/
    <module>/
      index.ts        ← the module's public API: the ONLY file others import
      service.ts      ← business rules (exchange window, price difference…)
      repository.ts   ← SQL for this module's own tables, nothing else
      schemas.ts      ← zod input/output validation
      types.ts
      events.ts       ← domain events it emits ('order.paid', 'stock.restocked')
  integrations/
    payments/      registry.ts · razorpay/ · mock/
    fulfillment/   registry.ts · qikink/  (· printrove/ later)
    email/         registry.ts · <provider>/
  platform/
    db.ts            ← pooled Neon client (server-only)
    http.ts          ← error envelope, request ids, pagination helpers
    auth.ts          ← session, withRole / withPermission / withGuestOrCustomer
    idempotency.ts   ← Idempotency-Key handling (idempotency_keys)
    events.ts        ← in-process event dispatcher
    jobs.ts          ← background workers (fulfilment poll, emails, alerts)
src/app/api/<module>/…/route.ts   ← thin: parse → guard → service → respond
```

### Module rules

1. **A module owns its tables** (map in `3.Database-Schema.md` §4). Only
   its `repository.ts` writes them.
2. **Modules talk through `index.ts` only.** No reaching into another
   module's repository or internals.
3. **Side effects go through events, not direct calls.** `orders` emits
   `order.paid`; `fulfillment` (submit to provider), `notifications`
   (email) and `gift-cards` (issue a purchased card) subscribe. Adding a
   new reaction = a new subscriber, no edit to `orders`.
4. **External services sit behind an interface + registry**
   (`integrations/<category>/registry.ts`), looked up by the
   `integration_providers.slug`. Adding a provider = adapter + DB row + env
   secrets (`DOC/backend/16-Fulfillment-Providers.md`).
5. **Route handlers hold no logic** (~30 lines): validate, guard, call one
   service function, shape the response.
6. **Invariants that both apps must respect live in SQL** (CHECKs, FKs,
   unique indexes), so the two backends cannot drift.

## 4. API conventions (summary)

- REST + JSON under each app's `/api`. No `/v1` until a second client
  exists.
- Errors: `{ error: { code, message, details[] }, requestId, timestamp }`.
- Pagination: storefront cursor, admin offset.
- Every mutating request carries `Idempotency-Key` (UUIDv7).
- Auth: 15-minute access token + 30-day rotating refresh token, per-app
  cookies, bcrypt password hashes.
- Money in JSON: rupees as strings with 2 decimals, or integer paise —
  one choice per API, converted at the boundary; the DB is always
  `DECIMAL(12,2)`.

## 5. Background work

No message broker in v1. Work is queued as rows the owning module already
has (`fulfillment_orders` with `status = 'pending'`, `email_logs` with
`queued`, `stock_alert_subscriptions` with `waiting`) and processed by
scheduled workers in the admin app (e.g. Vercel Cron). Every worker is
idempotent, so a retry never double-submits or double-emails.

## 6. Shared package (decided 2026-11-10)

Modules used by both apps live once in the workspace package
`packages/heart` (npm name `@tuw/heart`), bundled into each app's build —
never deployed on its own and owned by neither app.
